# TEST Channel: ввод периодического обнаружения

**Состояние на 2026-11-06:** ручная установка из UI квалифицирована на VM 120; периодическое обнаружение ещё **не введено**. Discovery timer выключен, временный токен удалён, `AUTO_UPDATE=false`. Этот документ описывает следующий отдельный операторский шаг, а не разрешение на production RELEASE или автоматическую установку.

## Действующий путь

`homecloud-update-discover.timer` запускает oneshot `homecloud-update-discover.service` через 2 минуты после загрузки и затем каждые 6 минут. Root-owned `update-host-discover.py` проверяет защищённый HEAD `test`, успешный push CI, действительный Actions artifact, манифест, исходные файлы, миграции и GHCR digests. Он не меняет checkout и не запускает установщик. При ошибке опубликованный кандидат удаляется; устаревший/небезопасный кандидат backend не принимает. Проверенный результат доступен backend только через read-only status mount. `GET /updates` доступен администратору и показывает установленную версию и кандидата; POST установки требует отдельного нажатия и повторной проверки хостом.

Backend в TEST host-профиле читает `available.json` и `installed.json` из host status; GitHub-токен ему и браузеру не передаётся. `current.json` с итогом прошлой установки остаётся до операторского разбора. Пока он имеет статус `INSTALLED`, UI показывает прошлый результат, но новую кнопку установки не предлагает: новая заявка требует `NO_JOB`.

## Минимальная последовательность на VM 120

1. После отдельного merge документального checkpoint дождаться успешной post-merge CI сборки защищённого `test`. На VM подтвердить установленный J, отсутствие pending/inbox, здоровые сервисы и `AUTO_UPDATE=false`. Новый защищённый commit нужен для проверки отображения кандидата: при одинаковых установленном и удалённом HEAD UI закономерно показывает «Новой сборки нет».
2. Создать токен только для этого репозитория с правами **Actions: read** и **Contents: read**; без write, `repo` или `workflow`. Actions нужны для [артефакта](https://docs.github.com/en/rest/actions/artifacts), Contents — для [сведений о защищённой ветке](https://docs.github.com/en/rest/branches/branches). Поместить `GH_TOKEN` в root-owned EnvironmentFile сервиса вне репозитория с режимом `0600`; проверить доступ к GitHub Actions artifact. GHCR-образы в текущем TEST контуре проверяются анонимно; не выдавать Packages write или более широкий токен. Если доступность образов изменится, остановиться и пересмотреть отдельные права чтения, сохраняя секрет вне backend и браузера.
3. Один раз запустить существующий discovery service. Требовать exit 0 и root-owned кандидат с `sourceGitSha` равным установленному J, `commit` равным защищённому TEST HEAD, корректным run/artifact/manifest identity и тем же набором 30 миграций. Ошибка/отсутствие кандидата — `STOP`, не подменять его вручную.
4. В административном разделе «Обновления» проверить установленную версию и новую проверенную TEST-сборку. Отдельно сверить `GET /updates` и отсутствие автоматической заявки на установку. Для появления кнопки перед **следующей** ручной установкой оператор должен сверить завершённый `INSTALLED` receipt J с фактическим HEAD, image IDs, журналом, данными и отсутствием pending, архивировать этот terminal receipt вне живого status path и проверить `NO_JOB`. Не очищать `RUNNING`, `STOP`, `MANUAL_RECOVERY_REQUIRED` или недостоверный receipt как рутинную операцию.
5. После двух успешных последовательных запусков discovery и проверки UI включить существующий timer. Проверить повторное срабатывание по журналу и обновление `checkedAt`; сохранить `AUTO_UPDATE=false`. Любая установка остаётся только явным действием администратора в UI.
6. При отказе отключить timer, сохранить диагностику и не объявлять кандидата доступным. При компрометации или завершении проверки отозвать токен и удалить его root-only файл. Отдельно сверять, что timer и token не включены на production или мини-ПК.

Код и systemd units для этого пути уже присутствуют; этап не требует нового updater или изменений в TEST installer. Операционное включение, токен и проверка периодичности остаются **открытыми** до отдельного E2E checkpoint.
