# Updates v1 — этап 1: версии и обнаружение

Этап не устанавливает обновления. Он не запускает Docker, миграции, backup или restore. Production остаётся `NO_GO`, Multi-Storage — `DEFERRED`.

## Контракт опубликованной версии канала `test`

Источник — существующий `release-lock.json` формата `homecloud-ci-candidate-v1` из `release.yml`. Его `tag` есть версия `v0.x.y-beta.n`, `commit` — полный Git SHA, `images.backend/frontend.digest` — точные GHCR digests, `schema_migrations` — контракт совместимости. Краткое описание изменений помещается в опубликованном GitHub prerelease под заголовком `## Изменения`. Это два элемента одного опубликованного release, без нового реестра версий и без изменения release workflow.

Существующий workflow создаёт **draft**, а не опубликованный release. Draft, один только Git tag, commit на `main`, offline artifact и старый локальный release `v0.9.0-local.1` не означают доступное обновление. Публикация draft остаётся отдельным решением владельца после review. На момент реализации опубликованного beta release канала `test` нет.

`GET /api/v1/updates` доступен только настроенному администратору. Backend проверяет, что release опубликован и помечен prerelease, lock имеет верный checksum и согласованные идентификаторы сборки/qualification, workflow `release.yml` завершился успешно с нужным SHA и attempt, annotated tag не перемещён, commit кандидата является потомком установленного, список миграций совпадает, а оба точных digest отвечают из GHCR. Сбой любой проверки скрывает кандидат. Доверенная граница — право записи в GitHub release и GHCR; криптографическая подпись release-lock не заявляется. Ответ не содержит GitHub token и не предлагает установку. `GET /api/v1/updates/access` сообщает только текущему аутентифицированному пользователю, доступен ли ему раздел.

## Конфигурация при будущем развёртывании этапа

- `UPDATE_ADMIN_USER_ID`: стабильный числовой ID администратора. Без него раздел выключен для всех. В текущей схеме HomeCloud нет ролей; это явная граница, а не скрытое предположение, что любой пользователь — администратор.
- `UPDATE_INSTALLED_LOCK_PATH`: путь **в контейнере backend** к read-only `release-lock.json` реально установленной сборки. Только проверенный lock принимается как установленная версия.
- Для существующего тестового deployment `ac1aca1`, у которого нет beta lock, вместо него допускается `UPDATE_INSTALLED_METADATA_PATH` к read-only JSON: `{ "format": "homecloud-installed-test-v1", "version": "ac1aca1", "gitSha": "<полный SHA фактически работающего commit>", "schemaMigrations": ["<точные имена применённых миграций>"] }`. `version` должен равняться первым семи символам `gitSha`. Этот файл является утверждением оператора о deployment, поэтому его нельзя создавать по текущему `main` без сверки с работающим сервером и БД. Пока файл не подключён, UI честно показывает «не определена» и не заявляет доступное обновление.
- `UPDATE_GITHUB_TOKEN` и `UPDATE_GITHUB_USER` нужны backend для закрытого репозитория/пакетов; токену достаточно чтения release, Actions и GHCR. В браузер он не передаётся. Без токена публичные release/packages могут проверяться анонимно. Переменные и read-only файл требуется передать контейнеру отдельно в разрешённом тестовом deployment; этот этап Compose и сервер не меняет.

API возвращает `status: installed_unknown | current | available | check_unavailable`. `current` означает отсутствие **проверенного совместимого** кандидата, а не отсутствие любых commits или tags. Сетевая ошибка отображается как неизвестность, не как «обновлений нет». Совместимость на данном этапе консервативна: точное совпадение имён миграций; возможные безопасные schema upgrades будут рассматриваться в другом этапе.
