## Массовое скачивание: контракт для согласования

Проверено в исходниках: `GET /api/v1/files/:id/download` скачивает один файл владельца; `POST /api/v1/sharing/public/:token/download` строит ZIP только для одной публично опубликованной папки. Маршрута, который принимает набор выбранных объектов владельца, нет. Публичный маршрут не подходит для приватного выделения: его вызов требовал бы создания ссылки и менял бы модель доступа.

Предлагаемый backend-контракт:

1. Аутентифицированный `POST /api/v1/files/download-archives/prepare` с телом `{ "items": [{ "kind": "file", "id": 12 }, { "kind": "folder", "id": 7 }] }`. ID папки — `FolderEntity.id`, не ID её зеркала в `files`. Сервер ограничивает число выбранных корней и глубину/число членов, проверяет каждый корень и каждого потомка на владельца и отсутствие soft delete до выдачи права на скачивание. В ответе — одноразовый краткоживущий путь/токен, связанный с пользователем и точным набором.
2. `GET` по подготовленному пути передаёт **один** ZIP через нативный менеджер браузера, без сборки архива в памяти клиента. Одноразовый токен, `Cache-Control: no-store`, безопасное имя, корректный `Content-Disposition`, ограничение одновременных архивов и отмена потока при отключении клиента. Повторная проверка доступа и физической целостности непосредственно перед потоком обязательна. Отдельно определить, можно ли возобновлять прерванный ZIP: базовый вариант — нет.
3. Внутри ZIP корни находятся на верхнем уровне; пустые папки включены; пути потомков сохранены. Если выбраны папка и её потомок, потомок включается один раз через папку. Совпадающие/опасные имена, `..`, абсолютные пути, управляющие символы и конфликты после нормализации требуют явной обработки с однозначным результатом либо отказом до начала потока.
4. До начала выдачи байтов сервер проверяет лимиты, доступность хранилища и безопасное открытие файлов. Существующую реализацию ZIP публичной папки можно использовать как основу, но нельзя переиспользовать её публичный token/download контур для приватных объектов.

Главные риски: дорогое рекурсивное перечисление и большой поток с нагрузкой на диск/CPU; изменение дерева между подготовкой и скачиванием; утечка чужих или удалённых данных при ошибке в проверке каждого потомка; коллизии путей; неполный архив при пропаже файла или разрыве соединения. Нужны адресные backend-тесты доступа, симлинков/путей, пустых папок, пересечённых выделений, лимитов и прерывания потока, затем frontend-интеграция одной кнопки «Скачать ZIP» в панель выделения.

Без согласования этого API массовое скачивание не реализовано. Несколько отдельных браузерных скачиваний не дают надёжного сохранения структуры и часто блокируются браузером.
