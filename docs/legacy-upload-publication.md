# Legacy upload: сборка и публикация — этап 3.0

Локальное исправление блокера Public Folder Sharing. Миграции и публичные upload
endpoints не добавлены; API-контракт этапа 1 сохранён. SSD/Multi-Storage не изменены.

## Причина и порядок блокировок

Прежний complete удерживал upload session `FOR UPDATE` во время чтения всех чанков,
затем запрашивал user lock для квоты. Hard-delete мог удерживать user lock и через
FK `SET NULL` ожидать ту же сессию. Цикл session → user / user → session давал `40P01`.

Теперь длительная сборка проходит без транзакции и без row locks. Выделенное
соединение PostgreSQL удерживает exclusive session advisory fence по uploadId.
Чтение chunk receipts и финальная транзакция используют это же соединение, поэтому
завершение работает и с pool.max=1. Короткие chunk/abort/reconcile/expiry операции
берут shared transaction advisory fence, затем прежний session row lock. Параллельные
повторы чанков сериализуются; при активной сборке изменяющие операции отвечают
`409` с предложением повтора, expiry cleanup пропускает занятую сессию.

Публикация и folder hard-delete/empty-trash используют порядок user → folders →
files/session. Soft-delete папки и permanent-delete файла также сначала берут user
lock. Сборка не блокирует удаление целевой папки; публикация после удаления отклоняется.

## Файл и восстановление

Каждая попытка пишет уникальный `.assembly-UUID` внутри существующего workspace
сессии. Проверки размера, SHA-256 чанков и целого файла, MIME и fsync выполняются
до начала транзакции публикации. Уникальный физический ключ содержит UUID попытки;
потерявшая PG-соединение старая попытка не удаляет результат новой.

Короткая транзакция повторно проверяет активного владельца, живую цепочку папок и
зеркал, исходный parentId, owner origin, статус/TTL/binding сессии и квоту с учётом
всех pending/uploading reservations. Атомарный выбор имени сохраняет общий namespace.
Сборка публикуется exclusive hard link; `.assembly-UUID` остаётся recovery marker до
commit. Каталог физического объекта синхронизируется до commit. File, storageUsed и
completed status фиксируются в одной транзакции. Резервирование превращается в
использованную квоту без повторного списания. Completed replay возвращает тот же файл;
исторический pending status при уже существующем оплаченном File восстанавливается.

При ошибке до COMMIT удаляются только собственные проверенные пути попытки, чанки
остаются пригодны для повтора. После неопределённого COMMIT объект сохраняется:
повтор проверяет File в БД и восстанавливает завершение либо убирает неопубликованную
попытку перед новой сборкой. Abort/TTL находят уникальные объекты по `.assembly-UUID`;
чужой или опубликованный объект не удаляется. Список попыток снимается до чтения File,
чтобы потерявшая fence очистка не захватила новую попытку. Очистка старых deterministic
legacy assemblies сохранена. Ошибка storage identity оставляет артефакты для проверки.

Потеря соединения освобождает advisory fence автоматически; runner не переподключается
для публикации старой попытки. Если снятие fence не подтверждено, pool client уничтожается.
Новые durable статусы, журнал БД или миграция существующих сессий не потребовались.

## Границы приёмки

- Сборка занимает одно соединение PostgreSQL на всё время операции.
- Hard link требует одной файловой системы для legacy workspace и объектов;
  cross-FS copy/fallback не добавлен. Ошибка публикации сохраняет чанки для повтора.
- Восстановление после аварии выполняется при retry, TTL cleanup или startup cleanup;
  это не квалификация power-loss, физического диска или нового storage placement.
- Production остаётся NO_GO; домашний сервер не обновлялся. Совместный запуск старого
  и нового upload core против одной БД не квалифицирован.
- Реальные сервисы проверяются с owner API. Test-only FK parentId→folders SET NULL в
  отдельной схеме воспроизводит зависимость session update исходного public FK;
  это не тест публичного API, который ещё не реализован.

Итоговые проверки и независимый review фиксируются в ROADMAP у checkpoint этапа 3.0.
