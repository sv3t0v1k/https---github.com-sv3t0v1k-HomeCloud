## Проверенные свойства

- **Pause и безопасное завершение текущего запроса.** `frontend/src/files/uploadQueue.ts:124`: Pause устанавливает намерение остановки и прерывает ожидания, но не отменяет выполняемый HTTP chunk и не вызывает серверный abort. Следующий chunk не планируется после проверки `stopped`. Состояние pausing переходит в paused после завершения текущей операции. Серверная сессия и reservation сохраняются. Тест `settles an in-flight chunk before paused; committed progress resumes the same session` проверяет принятый текущий chunk, отсутствие новых частей во время паузы и отсутствие DELETE.
- **Same-page и network Resume.** `uploadQueue.ts:133, 360`: сохраняется uploadId; перед продолжением выполняется GET reconciliation. Проверяются имя, размер, целевая папка, индексы/размеры частей, сумма uploadedSize и SHA-256 каждой принятой части выбранного файла. Принятые индексы пропускаются. Исчерпание ограниченных сетевых retries оставляет session и reservation; явное продолжение использует ту же сессию. Тесты проверяют единственный create и отсутствие повторной отправки уже принятого chunk.
- **Потерянный ответ создания.** `uploadQueue.ts:274, 343`: создание не повторяется автоматически при неопределённом результате. Discovery показывает серверную сессию отдельной строкой; пользователь выбирает исходный файл. Resume неопределённой локальной строки не создаёт дубликат. Это честная модель восстановления, а не обещание автоматической идентификации потерянного ответа.
- **Потерянный ответ финализации.** `uploadQueue.ts:330, 360`: без ответа finalization состояние не получает ложные 100%. Resume узнаёт completed и опубликованный файл через reconciliation без повторного create/finalize. При Cancel после потерянного ответа DELETE уже завершённой сессии может быть отклонён; дополнительный reconciliation распознаёт completed и не удаляет опубликованный файл. Регрессии проверяют обе ветки.
- **Reload и выбор исходного файла.** `uploadQueue.ts:172, 441, 462`: сохраняются безопасные метаданные, fingerprint и uploadId, без File bytes/JWT/паролей. После reload состояние needs-file требует повторного выбора; имя/размер и сохранённый sample fingerprint проверяются, затем сверяются все принятые chunks. Тест отклоняет неверное имя и содержимое. Исходный File не обещается восстановить без участия пользователя. Проверка sampled identity не является полным хешем всех ещё не отправленных байтов; обязательная проверка принятых chunks предотвращает смешивание несовместимого принятого префикса.
- **Сотни локально известных сессий.** `uploadQueue.ts:470`: restore обрабатывает все валидные сохранённые записи и не обрезает их до лимита серверного discovery. Регрессия 205 записей проверяет 205 восстановленных/сохранённых строк, отсутствие HTTP и одну запись storage. Ограничение серверного discovery 200 не уничтожает уже известные локальные сессии.
- **Retry-After и Pause.** `frontend/src/files/upload.ts:162`: notBefore записывается до проверки прерванного управляющего сигнала. Поэтому 429, пришедший после нажатия Pause во время in-flight chunk, сохраняет обязательное ожидание; Resume не повторяет запрос раньше срока. Retries и бюджет ожидания ограничены. Регрессии проверяют паузу во время backoff и паузу до запоздалого 429 с границей 1999/2000 мс.
- **Ограниченный параллелизм.** `uploadQueue.ts:66, 238`: не более двух активных файлов, по одному chunk на файл. Paused jobs освобождают слот после безопасного завершения текущей операции. Ошибка/Cancel одного файла не отменяет соседние. Тесты проверяют максимум два запроса, завершение соседей и сохранение target folder.
- **Cancel и reservation/chunks.** `uploadQueue.ts:402`: отдельный DELETE использует ограниченные повторы и deadline; неподтверждённая отмена не объявляется cancelled, сохраняет намерение и повторяется после reload. Backend abort удаляет принятые chunks/temp, а статус aborted исключает session из reservation. Подтверждённый DELETE обнуляет committedBytes (`uploadQueue.ts:426`), поскольку эти bytes больше не сохранены сервером. Регрессия сохраняет положительный прогресс при неподтверждённой отмене, затем проверяет 0 bytes/0 percent после подтверждения; completed после потерянного finalization ACK остаётся на 100%.
- **Достоверность прогресса.** Bytes растут после успешного серверного ответа chunk; 100% требует finalization/completed reconciliation. Discovery импортирует только отсутствующие сессии и не перезаписывает существующий прогресс запоздалым снимком. Соответствующая регрессия действительно задерживает ранее захваченный снимок до завершения загрузки.
- **Граница владельца и logout.** `frontend/src/api/client.ts:40, 62, 91`, `frontend/src/auth/tokenStorage.ts`: apiRequest синхронно фиксирует поколение владельца; interceptor не отправляет/не повторяет запрос после смены поколения. Обычный refresh сохраняет поколение владельца. Поздний неуспешный refresh старой сессии не очищает новую. Тесты проверяют задержанный 401 владельца A после входа B и немедленное переключение до асинхронного interceptor.
- **Backend reconciliation и целостность.** `backend/src/uploads/uploads.service.ts`: detail reconciliation ограничен `(uploadId, userId)` и берёт write lock session, сериализуя его с chunk/finalize/abort. Серверные records несут byteSize/SHA-256; повторный chunk с другим содержимым отклоняется. Публикация и fsync chunk предшествуют durable DB accounting. Reconciliation completed возвращает существующий файл, не повторяет квоту и сборку.
- **StrictMode и unmount.** Discovery позволяет повторный authenticated effect mount той же очереди; dispose означает сохранение метаданных/остановку планирования, а не Cancel. После logout новое поколение владельца предотвращает повтор старого запроса с новым токеном. Есть регрессия reactivation после dispose.
