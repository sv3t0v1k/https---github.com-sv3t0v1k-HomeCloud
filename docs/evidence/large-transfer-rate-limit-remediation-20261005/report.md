## Причина и исправление

Прежний global limiter ограничивал весь `/api/v1` по нормализованному client IP: 100 запросов за60с до JWT/multipart. Создание сессии, каждый chunk, повторная попытка и abort расходовали общий бюджет; на полном50ГиБ прогоне98 chunks прошли, chunk и abort получили429. Frontend не повторял429, а повторный owned abort отвечал400.

Обычный API сохраняет100/60с. Только канонические chunk POST и abort DELETE с проверенным JWT обходят прежний global bucket. Пользовательская transfer policy действует на все фактически обслуживаемые controller chunk/abort routes после обычного JwtGuard; некорректные варианты пути сохраняют global limit. Для transfer routes: chunk25/с burst50 на user ID; отдельный coarse IP admission100/с burst100 до JWT; максимум4 активных chunk-запроса на пользователя и32 на backend process. Abort имеет свой user bucket0,5/с burst10 и coarse IP10/с burst20; поэтому исчерпание chunk budget не блокирует owned cleanup. Каждая map ограничена10000 keys, idle expiry5мин; session ID/JWT rotation не создают отдельный пользовательский бюджет. Контрольные endpoints не освобождены от прежнего глобального limiter. Текущая реализация рассчитана на один backend process; для нескольких реплик нужен общий limiter store.

Frontend повторяет429 на том же chunk, соблюдает `Retry-After` (секунды/HTTP-date), максимум3 попытки, предел ожидания60с на retry и суммарный бюджет ожидания повторов5мин (без ограничения общей длительности upload session). При исчерпании показывает понятную ошибку и ограниченно вызывает abort. Multipart принимает ровно один field и один file; прерванный writer закрывается, поздно созданный temp удаляется. Owned повторный abort остаётся идемпотентным и восстанавливает прерванную очистку.
