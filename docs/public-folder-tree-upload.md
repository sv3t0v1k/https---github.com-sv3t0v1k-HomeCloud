# Public Folder Sharing — дерево, этап 4

Локальная backend-поддержка протокола дерева поверх API этапов 2–3. Отдельного
массового endpoint, серверного job/manifest store и второго upload engine нет.
Выбор папки, сбор манифеста браузером, очередь и отображение результата в продукте
относятся к этапу 5 и здесь не реализованы. В интеграционных тестах используется
синтетический вызывающий код с очередью из двух файлов.

## Протокол

База: `/api/v1/sharing/public/:token`, HTTPS, `X-Share-Upload-Proof`.
Получение/обновление proof: существующий `POST /upload-authorizations`.
Форматы запросов/ответов и ограничения файла: [этап 3](public-folder-upload-operations.md).

1. Вызывающая сторона до первой записи составляет неизменный манифест обнаруженных
   directory/file entries: до 1000 **всех** узлов, глубина до 32 компонентов, каждый
   logical relative path до 4096 UTF-8 bytes. Обнаруженные пустые каталоги включаются
   явно. Необнаруженный каталог и пустой файл не считаются успешно переданными.
2. Проверяет компоненты: имя после NFC/trim имеет 1–255 UTF-16 code units, не `.`/`..`,
   без slash/backslash и control U+0000–001F/U+007F–009F. Полный исходный путь должен
   быть относительным: без drive/UNC/absolute prefix, пустых компонентов и traversal.
   Неоднозначные и повторяющиеся после нормализации пути, file-as-parent отклоняются.
   Все родители представлены directory entries; их можно явно добавить до проверки
   общего лимита. Percent encoding повторно не декодируется: `%2e%2e` — буквальное имя,
   не `..`. Logical paths никогда не передаются файловой системе как storage paths.
3. До отправки сохраняет для каждого узла отдельный UUID `Idempotency-Key` и точный
   payload операции. Ключ не меняется после timeout/отказа и не используется для
   другого payload. Checkpoint привязан к одной ссылке и одному target folder ID;
   навигация или обновление proof не меняют target.
4. Создаёт каталоги сверху вниз через `POST /folders {parentId,name}`. Начальный
   mapping: пустой относительный путь → выбранный допустимый target ID. Для каждого
   source directory path сохраняет **возвращённый folder ID** и actual name. Дети
   используют этот ID, а не поиск по имени и не предположение о suffix. Коллизия
   создаёт отдельную папку; существующая папка не объединяется с импортом.
5. Для файлов использует `POST /uploads/session` с ID сопоставленного родителя,
   исходным basename, размером, chunkSize и SHA-256. Затем обычные chunk/status/complete
   API. Для протокола дерева вызывающая сторона передаёт `expectedSha256`; исторический
   API этапа 1 по-прежнему допускает его отсутствие. Повтор chunk сверяет index/hash;
   complete возвращает один и тот же опубликованный объект и фактическое имя файла.
6. Ограничивает число активных сессий и сборок, соблюдает 429/Retry-After. Не создаёт
   сразу все file sessions большого дерева: лимит pending/uploading — 128 на владельца,
   включая owner uploads и все ссылки. В тестах файловая очередь равна двум.

Полный манифест не передаётся backend. Его суммарные bounds проверяет вызывающая
сторона; сервер **не гарантирует** depth32/path4096/1000 nodes отдельного импорта.
Backend принимает только отдельное имя + числовой parent ID, проверяет живой scope
каждой операции и не разрешает обойти его с помощью logical path. Серверный общий
лимит 1000 receipts ссылки — отдельный ресурсный budget, не размер одного дерева.
Включая предыдущие импорты, он может остановить даже манифест менее 1000 узлов.

## Продолжение и частичный результат

Возобновление всегда начинается с повторной проверки/mkdir replay каталогов сверху
вниз с прежними ключами и payload. Сохранённый ID не позволяет пропустить проверку
родительской ветви. Parent mapping обновляется только после успешного ответа.
Если родитель не подтверждён, зависимые узлы получают `blocked`, но независимые
ветви могут продолжаться. Успешный replay сохраняет тот же ID и actual name.

Create-session replay восстанавливает известную сессию даже при потерянном ответе.
`GET /uploads/session/:uploadId` сверяет принятые chunks; повторяются только недостающие.
Если complete-ответ потерян, повтор complete возвращает прежний File, без двойной квоты
и без второго physical object. В незавершённой сессии target неизменяем.

Если владелец переместил созданный каталог или опубликованный файл в другую ветвь
**внутри** ссылки, replay возвращает 409 вместо незаметного изменения структуры.
Это проверяется для mkdir, create-session replay, completed status и complete.
При перемещении наружу, удалении или отзыве — отказ live authorization (обычно 404).
Посетитель не исправляет такое перемещение, не создаёт замену с новым ключом и не
удаляет результат. Возвращение объекта владельцем на исходное место может вновь
разрешить replay. Owner rename без изменения parent может вернуть новое actual name;
имена/размещение после законченного импорта не замораживаются от действий владельца.

Результат ведётся **по каждому исходному пути**: kind, state, actual ID/name,
известный uploadId и безопасный HTTP code при наличии ответа; транспортный код ошибки
хранится отдельно, без выдуманного HTTP500. Неизвестный результат запроса не отмечается
как success. Контрольные сведения/ключи хранятся отдельно от proof/пароля; credentials
остаются только в памяти. Серверного endpoint агрегированного результата нет.

| Состояние / причина | Следующее действие |
|---|---|
| `succeeded` | Объект опубликован; при resume перепроверить receipt/scope, не создавать новый |
| `failed`, timeout/5xx | Повторить тот же ключ/payload либо status известной сессии; результат может уже существовать |
| `failed`, 429 | Дождаться Retry-After; rate budget восстанавливается отдельно от cap receipts/pending |
| `failed`, истёк proof | Получить новый proof и повторить прежнюю операцию; не каждый 403 означает истёкший proof |
| `failed`, quota | Требуется освобождение/увеличение квоты владельцем, затем прежний ключ/session |
| `failed`, 400/hash/пустой файл | Исправление/отдельное решение; не выполнять слепой повтор и не считать success |
| `failed`, 404/409 изменения scope/result | Остановить зависимую ветвь и сообщить причину; не подменять mapping |
| `blocked` | Не отправлен из-за неподтверждённого родителя; продолжить только после его восстановления |

Receipt хранится минимум 24 часа, затем bounded cleanup может удалить его. После TTL
неопределённый create нельзя автоматически повторять даже с прежним ключом: tombstone
не бессрочный. Повтор с новым ключом также создаст дубликат. На cap receipts точный
живой replay разрешён; новые операции блокируются до освобождения budget. Чанки/
сессии имеют собственный TTL. Восстановление после закрытия вкладки/рестарта клиента
не обещано: backend receipts не заменяют утраченный checkpoint и исходные bytes.

Импорт **не атомарен целиком**: mkdir и публикация каждого файла фиксируются отдельно.
Отзыв/перемещение/частичный отказ сохраняют уже опубликованное у владельца. Автоматического
rollback дерева нет. Abort отменяет только незавершённую известную сессию и освобождает
её reservation; не удаляет папки или опубликованные файлы. Завершённые узлы не означают,
что передано всё дерево. Предсуществующие объекты не перезаписываются и не изменяются.

## Серверные изменения и границы квалификации

- `PublicFolderService` считает **все** receipts ссылки, согласованно с file-session
  create; общий user/share lock сериализует смешанные mkdir/file операции на cap1000.
- Проверки ожидаемого parent для повторов выявляют owner move внутри дерева, сохраняя
  существующую live scope проверку и owner API. C1 control имена папок отклоняются,
  как уже отклонялись upload core для файлов. Миграций и новых маршрутов нет.
- Обычные запросы ограничены 100/min/IP, public60/min/IP и 30/min/token; password/
  download/proof/children делят дополнительный attempt budget10/min. Verified chunks
  и abort используют отдельные bounded budgets этапа 3. Большое дерево требует pacing;
  1000 узлов не обещают завершение за минуту. 429 не означает rollback уже созданного.
- Admission остаётся **в одном процессе**, без распределённой координации реплик.
  Public complete требует pool≥3. При pool3 лимит одной сборки; при достаточном pool
  — до двух общих с owner. Dedicated connection занято на всю сборку. Реальные
  тесты проверяют pool<3, освобождение admission, две сборки и возможность revoke.
- Hard link требует одной файловой системы workspace/destination. Linux local storage
  проверен, EXDEV отклоняется без copy fallback; домашний mount/NAS/power-loss не проверены.
- Proof действует до пяти минут и снова проверяется перед публикацией. Тест с переводом
  часов на шесть минут подтверждает отказ без публикации и возобновление из chunks после
  нового proof. **Реальная успешная сборка длительностью более пяти минут не квалифицирована**;
  повтор может снова не успеть. Новый механизм продления/finalizer не добавлялся.
- Пустые файлы не поддерживаются. Явные пустые directory entries поддерживаются через
  mkdir. Реальные возможности folder picker/обнаружения пустых каталогов — этап 5.

Итоговые Linux/PostgreSQL результаты, независимый review и checkpoint — в ROADMAP.
Production NO_GO и Multi-Storage DEFERRED сохраняются. Домашний сервер, CI/CD,
frontend не изменялись; push/merge/release/deployment не выполнялись. После этапа 4
остановка; этап 5 требует отдельного согласования.
