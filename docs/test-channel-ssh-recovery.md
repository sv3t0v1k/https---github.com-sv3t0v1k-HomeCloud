# TEST Channel: передача установки службе systemd

Статус: подготовлено для изолированной приёмки, **не разрешает автоматический deploy**.

## Контракт

- `project-test.sh test-submit` читает ограниченный по размеру JSON с stdin, проверяет контракт, сохраняет `ssh-manifest.json` (`root:0600`) и `ssh-job.json` (`root:0600`) в существующем `.runtime/test-channel` (`root:0700`).
- Отдельная systemd-служба `homecloud-test-apply-<32 hex>.service` выполняет `test-job.py worker <64 hex>` без `--pipe`, PTY и пользовательского SSH stdin. Содержимое манифеста **не** включается в аргументы процесса.
- `project-test.sh test-job-status` выдаёт только `manifest_sha256` и итоговый статус. `INSTALLED` устанавливается **только** после успешного исполнения и проверки `state.json` и отсутствия `pending.json`.
- Пока статус `QUEUED`/`RUNNING`, новые различные задания запрещены. Повторение **того же** манифеста возвращает статус, не запускает вторую службу.
- `STOP` и `UNKNOWN_REQUIRES_REVIEW` требуют оператора. Никакого автоматического rollback, перезапуска задания или очистки `pending.json`.

## Обязательные условия перед первым запуском

1. На мини-ПК есть systemd и бинарники `/usr/bin/systemd-run`, `/usr/bin/systemctl`, `/usr/bin/python3`. Проверка на настоящем хосте пока **не проведена**.
2. Путь `/home/hs/homecloud-test` и исполняемые скрипты защищены от изменения SSH-пользователем, а `.runtime` и `.runtime/test-channel` принадлежат root и имеют `0700`.
3. Ключ для GitHub Actions привязан к *принудительному* SSH-командному диспетчеру, который разрешает **только** точные команды `sudo -n /home/hs/homecloud-test/deploy/linux/project-test.sh test-submit` и `sudo -n /home/hs/homecloud-test/deploy/linux/project-test.sh test-job-status`. Никакого произвольного shell, аргументов, SSH forwarding или PTY; диспетчер и политика sudoers должны быть root-owned и не доступны для записи SSH-пользователю.
4. Сам код `test-job.py` сначала установлен вручную безопасным способом, поскольку старый checkout на мини-ПК не содержит новых команд.
5. Инициализированы/одобрены state, mounts, backup и recovery. Выполнена отдельно проверка `systemd-run` на изолированном хосте, включая реальный разрыв SSH.
6. `TEST_AUTO_DEPLOY_ENABLED` остаётся `false`, пока не подписана эксплуатационная приёмка.

## Диагностика после потери SSH

Использовать только ограниченную команду `test-job-status`; сопоставить `manifest_sha256` с манифестом GitHub Actions. `UNKNOWN_REQUIRES_REVIEW` означает, что живой процесс не подтверждён — **не повторять установку автоматически**. Оператор сверяет `ssh-job.json`, `pending.json`, `last-status.json`, `state.json`, `journalctl` соответствующей systemd-службы, Git checkout, конфигурацию образов и резервную копию. `recovery-inspect` остаётся чтением без восстановления; любые изменения — отдельная ручная процедура.

## Предел доказательств

Локальные unit-тесты проверяют состояние, аргументы вызова systemd и обработку отказов с заглушками. Они не доказывают поведение настоящего systemd, потери сети, перезапуска машины, доступности Docker или сохранности данных. До включения автоматизации эти пункты проверяются вручную в безопасной TEST-среде.
